📑 Pitch Summary

Import a CDISC USDM v4.0 study file directly into a new USDM Workbench in P21 and expose it through three read-only views: an interactive Study Summary, an ICH M11-style Schedule of Activities, and a Biomedical Concept (BC) to CRF Specialization mapping view. The COSMoS BC catalog is the join key that ties a scheduled protocol activity to a candidate CRF question (cosmos_crf_item) with no manual mapping step required. SDTM dataset specialization, Value Level Metadata / WhereClause generation, and Define-XML output are explicitly out of scope for this build — this pitch targets the protocol-and-CRF side of the problem only.

Problem

  • USDM is CDISC's structured digital protocol standard, but P21 has no USDM Workbench today to ingest a USDM file. A study team member has to read the SoA and study design out of a Word or PDF protocol document rather than query it.
  • COSMoS Biomedical Concepts are designed to anchor protocol activities to standardised CRF and SDTM metadata, but without an ingestion and mapping view, that connection is theoretical — it exists in the standards, not in a tool a study team can actually browse.
  • Answering "what does this activity actually collect on the CRF" today means manually cross-referencing the protocol, the COSMoS BC catalog, and the CRF Specialization spreadsheet. There is no single place to browse the chain from Activity → BC → CRF question.

🗺️ Theme / Framing

Full SDTM dataset specialization support and Define-XML generation are valuable end states, but they are a materially larger body of work — Value Level Metadata, WhereClause generation, codelist subsetting — that depends on a USDM import layer existing first. Building both at once risks a long cycle with nothing concrete to review partway through.

This pitch targets the narrower, protocol-and-CRF-side slice: get a USDM file into the USDM Workbench, let a user browse it the way they'd browse any other spec object, and prove that the BC → CRF Specialization bridge is real and traceable rather than aspirational. SDTM mapping is a plausible next step once this foundation exists, but nothing here assumes or commits to that follow-on.

👤 Persona / Customers

  • Study build / data management teams onboarding a new study, wanting to see study design and SoA content without opening the protocol document.
  • CRF designers evaluating how much of a standard form library could be auto-populated from BC linkage before authoring a form from scratch.
  • Standards / metadata teams assessing COSMoS CRF Specialization coverage against a real study's BC list, to understand where gaps remain.

🏆 What Does Success Look Like?

  • A user can point the USDM Workbench at a USDM v4.0 JSON file and immediately see a Study Summary of its contents — epochs, arms, SAIs, activities, BCs — without hand-parsing JSON.
  • Clicking any summary figure opens the underlying record set as a table, rather than leaving the user with only a static count.
  • A Schedule of Activities renders in the familiar ICH M11 layout — epoch band, arm/treatment row, visit row, day row — directly from the USDM timeline objects, with activities grouped by category where a source for that grouping exists (see Design and Risks below).
  • Selecting a BC (or an activity) surfaces the matching cosmos_crf_item rows — domain, crf_group_id, crf_item, question text — so a user can see which CRF questions a BC resolves to without cross-referencing spreadsheets.
  • Where a bc_id resolves to more than one crf_group_id, the user chooses which one applies rather than the system guessing — most often this is a presentation choice (e.g. a panel laid out horizontally vs vertically) rather than a different clinical context, and Activity context or BC-level detail (e.g. a BC already named "Supine Blood Pressure" rather than a generic "Blood Pressure") can narrow the options before the user has to decide.
  • Coverage gaps are visible, not hidden: where a BC has no CRF Specialization match, the view says so plainly rather than silently returning nothing.

🎨 Design

Entry Point

From the P21 home screen, an Import USDM Study action accepts a USDM v4.0 JSON file and opens the USDM Workbench, with three read-only views scoped to that study.

1. Study Summary View

Parses studyVersion / studyDesign into a header (title, indication, phase, design) plus a row of clickable summary tiles: Epochs, Arms, Encounters, Scheduled Activity Instances (SAI), Activities, Biomedical Concepts, BC Surrogates.

Interaction Behaviour
Click a tile Expands a table of the underlying USDM records for that entity — e.g. clicking Activities lists activity name and BC-link count per activity
BiomedicalConcept vs BcSurrogate Counted and browsable separately — where no SDTM Dataset Specialization is published yet, USDM represents the concept as a BcSurrogate (reference = "None set"); collapsing this into the BC count would hide a coverage gap this view is meant to surface
ScheduledActivityInstance (SAI) vs Encounter Kept as separate tiles/tables rather than merged. ScheduledActivityInstance.name — not Encounter.name — is what actually drives the Schedule of Activities columns, and a single Encounter can span multiple SAIs; the SAI table carries the timing detail (timing_day, timing_type) that the SoA and BC-linkage views depend on

2. Schedule of Activities View

Row / Header Source
Epoch band StudyEpoch sequence
Arm / treatment row StudyArm × StudyCell
Visit column header ScheduledActivityInstance.name — not Encounter.name
Day row USDM timing objects on the timeline
Activity rows Listed in timeline order by default; cell badge shows the count of BC + surrogate links for that activity. Grouping by category is a stretch goal, not a given — see note below and Risks

On activity category grouping: earlier exploratory work grouped activities into categories (Safety, Lab, Admin, etc.), but that grouping was authored manually rather than read from a defined USDM field. USDM's BiomedicalConcept / BcCategory class could plausibly supply this structure where a study's BCs are categorised, but population of that class is optional and not guaranteed across sponsor USDM files. This build should not assume category grouping is available out of the box — it needs an explicit fallback (e.g. flat, timeline-ordered activity rows) for files where no category source exists, with grouped-by-category as an enhancement where BcCategory is populated.

This view renders the Main Timeline only. Sub-timelines (e.g. an intra-day PK sampling schedule) are a known extension point, not covered in this build — see Risks below.

On the SDTM-labelled columns: sdtm_target_variable and sdtm_annotation are fields that already exist on the CRF Specialization row itself (cosmos_crf_item) — displaying them here is read-only annotation surfaced from the CRF side of the specialization, not a build of the separate SDTM Dataset Specialization, VLM, or WhereClause objects. That distinction still holds per the No-Gos below: this view shows what the CRF Specialization already says about its SDTM target, it does not resolve vlm_group_id into the SDTM Dataset Specialization.

Example — a _NORMALIZED crf_group_id is not a single-item answer: a natural assumption is that resolving to one crf_group_id means one CRF item. That holds for denormalized groups (one BC, one row-per-concept, e.g. SYSBP_DENORMALIZED for a single Vital Signs measurement), but normalized groups span the whole set of variables collected for a domain in one Section, with a single Concept as the domain-level BC anchor. For a Concomitant Medications BC resolving to CMFREE_NORMALIZED, the result set looks like this:

Domain crf_group_id crf_item Question text
CM CMFREE_NORMALIZED CMTRT Reported Name of Drug, Medication, or Therapy
CM CMFREE_NORMALIZED CMDOSE Dose
CM CMFREE_NORMALIZED CMDOSU Dose Units
CM CMFREE_NORMALIZED CMROUTE Route of Administration
CM CMFREE_NORMALIZED CMSTDTC Start Date/Time of Medication

Five distinct CRF items, all under the one crf_group_id. The view must always render the full result set for a crf_group_id with a visible item count (e.g. "5 items in this group"), rather than a layout that implies or defaults to a single row — a user reading only the first result could otherwise wrongly conclude the BC maps to a single CRF field.

A bc_id can also resolve to more than one CRF Specialization outright — before the crf_group_id layout question even arises, the same bc_id can match multiple distinct specializations (different domains, different vlm_group_id values), for example a glucose BC with specializations in both an LB (Laboratory) and an FA (Findings About) context. Activity context and BC category are what disambiguate this first: the Activity a BC is scheduled under (e.g. Chemistry vs Urinalysis) and, where populated, the BC's own category classification, can narrow which specialization is the relevant one. Neither is guaranteed to fully resolve the match on its own, so the mapping view must be able to show more than one CRF Specialization result for a single bc_id and let Activity/category act as a filter or sort rather than a silent auto-pick — with the user making the final call where ambiguity remains, consistent with the crf_group_id selection behaviour below.

User agency where a bc_id maps to more than one crf_group_id: a single BC can legitimately resolve to multiple CRF layout groups in the master specialization. Most commonly this reflects a presentation choice rather than a different clinical concept — the same set of variables laid out as a horizontal panel (one row per measurement) versus a vertical/repeating block. Whether this ambiguity arises at all depends on how granular the sponsor's specializations are: some specializations already encode the distinguishing context at the BC level (e.g. a BC named "Supine Blood Pressure" rather than a generic "Blood Pressure" with a position qualifier), in which case the BC selection itself resolves the group and no further choice is needed. Where genuine ambiguity remains, Activity context (e.g. a "Supine Vitals" activity vs a "Standing Vitals" activity) and BC category can narrow the candidate list, but the view presents the remaining candidate crf_group_id groups side by side and requires the user to make the final selection rather than guessing on their behalf. Where only one crf_group_id matches, no selection step is needed and the single group is shown directly.

Where no match exists, the view states "No published CRF Specialization" rather than returning an empty table. This is a read-only lookup — no form generation, no editing, no save-back to the CRF spec.

Expected downstream link — P21 Form Spec library: crf_group_id is expected to link directly downstream to a Section in a P21 Form Spec library in a later phase — it is the natural join key between this mapping view and an existing or generated form. This build does not create, link, or write to any Form Spec object; it only surfaces crf_group_id as a stable, human-readable value so that connection can be made later without reworking the mapping view's data model.

✍️ Starter Pack of Requirements

  • USDM v4.0 JSON parser — extract studyVersion, epochs, encounters, activities, StudyCells/arms, ScheduleTimeline + ScheduledActivityInstance, biomedicalConceptIds, and bcSurrogateIds into USDM Workbench-native tables.
  • ScheduledActivityInstance (SAI) reference table — kept as its own browsable table, distinct from Encounters; carries SAI.name, timing_day, timing_type, and epoch/encounter linkage, since SAI (not Encounter) is what drives the Schedule of Activities columns.
  • COSMoS BC catalog reference table — bc_id, code, vlm_group_id — loaded once and referenced by the mapping view.
  • COSMoS CRF Specialization reference table (cosmos_crf_item) — imported from the COSMoS GitHub export or the CDISC Library API, keyed on bc_id.
  • Study Summary UI — stat tiles with click-to-expand table behaviour.
  • Schedule of Activities renderer — pivot of activity × ScheduledActivityInstance, with epoch/arm/day header rows.
  • BC → CRF Specialization lookup UI — selector, filtered result table, an explicit "no match" state, support for more than one matching CRF Specialization per bc_id (using Activity context and BC category to filter/sort candidates rather than assume a single result), and a crf_group_id selection step within the chosen specialization where it resolves to more than one candidate layout group, so the user — not an automatic rule — makes the final call at each level.
  • crf_group_id modelled as a stable, joinable field — no linkage is built to a P21 Form Spec library in this phase, but the value must be persisted in a form that a later phase can join against without a data model change.
  • Result set display, not single-row display, for a resolved crf_group_id — normalized groups (e.g. CMFREE_NORMALIZED) can return many crf_item rows for one group; the UI must show the full set with a visible item count so users aren't misled into thinking one crf_group_id equals one CRF item.
  • All three views are read-only in this build — no editing, no save-back.

🐰 Risks & Rabbit Holes

Internal Factors

Sub-timelines are commonly disconnected — intra-day or procedure-level sub-timelines (e.g. a PK sampling schedule) frequently exist in a USDM file as standalone objects with SAI.sub_timeline_id left null, so they will not automatically wire into the Main Timeline SoA. This build renders the Main Timeline only; sub-timeline linkage is a known gap to state clearly, not solve here.

CRF Specialization coverage is genuinely partial — the COSMoS CRF Specialization draft covers 16 domains (2,073 rows), but coverage within domains such as Laboratory is incomplete. The mapping view must surface "no match" honestly rather than imply full coverage exists.

A single bc_id can match more than one CRF Specialization outright, not just more than one layout group — the same bc_id can appear in genuinely distinct specializations (different domains, different vlm_group_id). Activity context and BC category are the intended disambiguators, but neither is guaranteed to be conclusive or even present, so the mapping view cannot assume it will always land on a single specialization before the crf_group_id question is even reached. This needs its own explicit UI treatment (a results list, not a single-row assumption) rather than being folded silently into the crf_group_id selection step below.

A single bc_id can map to more than one CRF Specialization group — vlm_group_id to crf_group_id is 1:many in some cases, most often because the same variables are laid out differently (horizontal vs vertical panel) rather than representing genuinely different clinical content. Whether this surfaces at all depends on how granular the sponsor's specializations are, and how much disambiguating context already lives at the BC level (e.g. "Supine Blood Pressure" as its own BC vs a generic BP measure) or the Activity level. This build resolves any remaining ambiguity through explicit user selection rather than an automatic best-match rule; the UI needs to make the choice unmissable (not a quiet default) so a user isn't misled into thinking only one layout group exists.

BcSurrogate vs BiomedicalConcept must stay visually distinct — collapsing them into a single count in the Study Summary would hide exactly the coverage-gap information this pitch is meant to surface.

Activity category grouping is not a guaranteed USDM feature — the protocol-category groupings used in earlier exploratory work (Safety, Lab, Admin, etc.) were authored manually, not read from a defined field. USDM's BcCategory class is a plausible native source for this grouping, but it's optional and sponsors may not populate it consistently, so it cannot be relied on as a given. Design and estimation should treat category grouping as a conditional enhancement, with a flat/timeline-ordered activity list as the guaranteed baseline.

External Factors

COSMoS CRF Specialization is still a draft standard; domain coverage will change over time, so the "no match" state in the mapping view needs to age gracefully rather than requiring UI rework each time CDISC publishes a new domain.

USDM files from different sponsors will vary in completeness and quality — missing sub-timeline links, absent BC references, partial activity metadata. The import step needs to fail gracefully on partial or malformed files rather than blocking the whole import.

❌ No-Gos & Out of Scope

  • SDTM Dataset Specialization mapping (sdtm_odm_item_def).
  • The vlm_group_id bridge to SDTM Dataset Specialization. vlm_group_id is the shared key linking a BC to both its CRF Specialization (via crf_group_id) and its SDTM Dataset Specialization — this build resolves the CRF side of that bridge only (bc_id → vlm_group_id → crf_group_id → cosmos_crf_item). Resolving vlm_group_id onward into the SDTM Dataset Specialization (variable role, assigned value, origin type, VLM target flag) is not built here and is a prerequisite for any future SDTM mapping view.
  • Value Level Metadata / WhereClause generation (odm_value_list, odm_where_clause).
  • Define-XML or SDTM trial domain generation (TA/TE/TV/TI/TS).
  • Any editing or save-back capability — all three views are read-only.
  • Sub-timeline-aware SoA rendering (PK sampling schedules, insulin clamp sub-schedules, etc.).
  • Automatic CRF form generation or any write/link to a P21 Form Spec library — the mapping view shows candidate matches and surfaces crf_group_id as the expected future join key, but does not create, link, or generate a form in this build.
