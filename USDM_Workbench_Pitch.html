📑 Pitch Summary

Import a CDISC USDM v4.0 study file directly into a new USDM Workbench in P21 and expose it through four read-only views: an interactive Study Summary, an ICH M11-style Schedule of Activities, a BC → CRF Specialization mapping view, and a BC → SDTM Dataset Specialization mapping view. The COSMoS BC catalog is the join key that ties a scheduled protocol activity to both its candidate CRF questions (cosmos_crf_item) and its SDTM dataset specialization variables (cosmos_sdtm_item) — with vlm_group_id acting as the shared bridge between the two sides. Everything in this pitch is read-only browsing: no form generation, no define generation, no VLM or WhereClause construction, no Define-XML output. Those are covered in Framing Pitch 2.

Problem

  • USDM is CDISC's structured digital protocol standard, but P21 has no USDM Workbench today to ingest a USDM file. A study team member has to read the SoA and study design out of a Word or PDF protocol document rather than query it.
  • COSMoS Biomedical Concepts are designed to anchor protocol activities to standardised CRF and SDTM metadata, but without an ingestion and mapping view, that connection is theoretical — it exists in the standards, not in a tool a study team can actually browse.
  • Answering "what does this activity collect on the CRF, and what SDTM variables does it produce?" today means manually cross-referencing the protocol, the COSMoS BC catalog, the CRF Specialization spreadsheet, and the SDTM Dataset Specialization. There is no single place to browse the full chain from Activity → BC → CRF question → SDTM variable.

🗺️ Theme / Framing

This is Framing Pitch 1 of 2. It establishes the read path: get a USDM file into P21, browse its study design and schedule, and make the COSMoS specialization bridge — both the CRF side and the SDTM side — visible and traceable in one place.

Framing Pitch 2 then establishes the write path: use the confirmed mappings from this pitch to generate real P21 artefacts — a CRF form object, an SDTM study define, and the five trial design domains. Nothing in Pitch 1 assumes or commits to that follow-on, but the data model this pitch establishes (vlm_group_id as the shared bridge key, crf_group_id as the CRF join, cosmos_sdtm_item as the SDTM join) is exactly what Pitch 2 consumes.

Splitting the two keeps each build reviewable independently. Pitch 1 is completeable without Pitch 2 ever being built; Pitch 2 cannot be built without Pitch 1 existing first.

👤 Persona / Customers

  • Study build / data management teams onboarding a new study, wanting to see study design and SoA content without opening the protocol document.
  • CRF designers evaluating how much of a standard form library could be auto-populated from BC linkage before authoring a form from scratch.
  • SDTM programmers / define authors wanting to see which SDTM variables a given protocol activity's BCs resolve to, without cross-referencing the specialization spreadsheet manually.
  • Standards / metadata teams assessing COSMoS CRF and SDTM Specialization coverage against a real study's BC list, to understand where gaps remain on each side.

🏆 What Does Success Look Like?

  • A user can point the USDM Workbench at a USDM v4.0 JSON file and immediately see a Study Summary of its contents — epochs, arms, SAIs, activities, BCs — without hand-parsing JSON.
  • Clicking any summary figure opens the underlying record set as a table, rather than leaving the user with only a static count.
  • A Schedule of Activities renders in the familiar ICH M11 layout — epoch band, arm/treatment row, visit row, day row — directly from the USDM timeline objects, with activities grouped by category where a source for that grouping exists (see Design and Risks below).
  • Selecting a BC (or an activity) surfaces the matching cosmos_crf_item rows — domain, crf_group_id, crf_item, question text — so a user can see which CRF questions a BC resolves to without cross-referencing spreadsheets.
  • The same BC selection also surfaces the matching cosmos_sdtm_item rows — domain, sdtm_variable, vlm_group_id, assigned value, value list — so a user can see which SDTM variables and VLM conditions the BC produces, in the same view.
  • vlm_group_id is visible as the shared bridge linking a BC's CRF Specialization and its SDTM Dataset Specialization, so the connection between the two sides is explicit rather than implied.
  • Coverage gaps are visible, not hidden: where a BC has no CRF Specialization match, or no SDTM Dataset Specialization match, the relevant view says so plainly. BcSurrogates (no published SDTM Specialization) are counted and displayed separately from BiomedicalConcepts in the Study Summary tile.
  • Where a bc_id resolves to more than one crf_group_id, the user is shown all candidates rather than a silent default — see Design below.

🎨 Design

Entry Point

From the P21 home screen, an Import USDM Study action accepts a USDM v4.0 JSON file and opens the USDM Workbench, with four read-only views scoped to that study.

1. Study Summary View

Parses studyVersion / studyDesign into a header (title, indication, phase, design) plus a row of clickable summary tiles: Epochs, Arms, Encounters, Scheduled Activity Instances (SAI), Activities, Biomedical Concepts, BC Surrogates.

Interaction Behaviour
Click a tile Expands a table of the underlying USDM records for that entity — e.g. clicking Activities lists activity name and BC-link count per activity
BiomedicalConcept vs BcSurrogate Counted and browsable separately — where no SDTM Dataset Specialization is published yet, USDM represents the concept as a BcSurrogate (reference = "None set"); collapsing this into the BC count would hide a coverage gap this view is meant to surface
ScheduledActivityInstance (SAI) vs Encounter Kept as separate tiles/tables rather than merged. ScheduledActivityInstance.name — not Encounter.name — is what actually drives the Schedule of Activities columns, and a single Encounter can span multiple SAIs; the SAI table carries the timing detail (timing_day, timing_type) that the SoA and specialization-linkage views depend on

2. Schedule of Activities View

Row / Header Source
Epoch band StudyEpoch sequence
Arm / treatment row StudyArm × StudyCell
Visit column header ScheduledActivityInstance.name — not Encounter.name
Day row USDM timing objects on the timeline
Activity rows Listed in timeline order by default; cell badge shows the count of BC + surrogate links for that activity. Grouping by category is a stretch goal, not a given — see note below and Risks

On activity category grouping: earlier exploratory work grouped activities into categories (Safety, Lab, Admin, etc.), but that grouping was authored manually rather than read from a defined USDM field. USDM's BiomedicalConcept / BcCategory class could plausibly supply this structure where a study's BCs are categorised, but population of that class is optional and not guaranteed across sponsor USDM files. This build should not assume category grouping is available out of the box — it needs an explicit fallback (e.g. flat, timeline-ordered activity rows) for files where no category source exists, with grouped-by-category as an enhancement where BcCategory is populated.

This view renders the Main Timeline only. Sub-timelines (e.g. an intra-day PK sampling schedule) are a known extension point, not covered in this build — see Risks below.

3. BC → CRF Specialization Mapping View

Selecting a bc_id — directly, or via drill-down from an Activity in the Study Summary — filters cosmos_crf_item to matching rows.

Column Source
Domain cosmos_crf_item.domain
CRF group cosmos_crf_item.crf_group_id
CRF item cosmos_crf_item.crf_item
Question text cosmos_crf_item.question_text
Mandatory cosmos_crf_item.mandatory_variable
SDTM target variable cosmos_crf_item.sdtm_target_variable
SDTM annotation cosmos_crf_item.sdtm_annotation
Codelist cosmos_crf_item.codelist
Codelist submission value cosmos_crf_item.codelist_submission_value
Value list cosmos_crf_item.value_list
vlm_group_id cosmos_crf_item.vlm_group_id — shared bridge key linking this CRF specialization to its counterpart in the SDTM Specialization view
Prepopulated term cosmos_crf_item.prepopulated_term

On the SDTM-labelled columns: sdtm_target_variable and sdtm_annotation are fields that already exist on the CRF Specialization row itself — displaying them here is read-only annotation surfaced from the CRF side of the specialization, not a build of the separate SDTM Dataset Specialization. This view shows what the CRF Specialization already says about its SDTM target; the SDTM Specialization view (below) provides the full SDTM-side picture.

Example — a _NORMALIZED crf_group_id is not a single-item answer: a natural assumption is that resolving to one crf_group_id means one CRF item. That holds for denormalized groups (one BC, one row-per-concept, e.g. SYSBP_DENORMALIZED for a single Vital Signs measurement), but normalized groups span the whole set of variables collected for a domain in one Section. The view must always render the full result set for a crf_group_id with a visible item count (e.g. "5 items in this group"), rather than a layout that implies or defaults to a single row.

A bc_id can resolve to more than one CRF Specialization outright — before the crf_group_id layout question even arises, the same bc_id can match multiple distinct specializations (different domains, different vlm_group_id values). Activity context and BC category are the intended disambiguators; neither is guaranteed to be conclusive, so the mapping view shows more than one result and lets Activity/category act as a filter rather than a silent auto-pick.

User agency where a bc_id maps to more than one crf_group_id: where genuine ambiguity remains after Activity context and BC category have been applied, the view presents the remaining candidate crf_group_id groups side by side and requires the user to make the final selection. Where only one crf_group_id matches, no selection step is needed and the single group is shown directly.

Where no match exists, the view states "No published CRF Specialization" rather than returning an empty table. This is a read-only lookup — no form generation, no editing, no save-back to the CRF spec.

Expected downstream link — Framing Pitch 2: crf_group_id is the join key that Pitch 2 uses to drive CRF form generation. This build surfaces it as a stable, human-readable value so that connection can be made without reworking the mapping view's data model.

4. BC → SDTM Specialization Mapping View

Selecting a bc_id — directly, or via drill-down from an Activity — filters cosmos_sdtm_item to matching rows, showing the full SDTM Dataset Specialization picture for that BC alongside the CRF view.

Column Source
Domain Derived from cosmos_sdtm_item.sdtm_variable prefix (e.g. VS, LB)
SDTM variable cosmos_sdtm_item.sdtm_variable
vlm_group_id cosmos_sdtm_item.vlm_group_id — the shared key that links this row to the corresponding CRF Specialization in View 3
Assigned value cosmos_sdtm_item.assigned_value — a fixed submission value for this variable in this specialization (e.g. mmHg for VSORRESU)
Value list cosmos_sdtm_item.value_list — the set of permitted test codes or submission values where a where-clause condition applies
Codelist cosmos_sdtm_item.codelist
Mandatory cosmos_sdtm_item.mandatory_variable
DEC cosmos_sdtm_item.dec_id — Data Element Concept identifier linking the variable to the BC's concept definition

The vlm_group_id bridge: vlm_group_id is the key that connects the two specialization views. A BC whose CRF Specialization resolves to crf_group_id = SYSBP_DENORMALIZED carries the same vlm_group_id as its SDTM Specialization rows (e.g. SYSBP). Displaying this key explicitly in both views — rather than hiding it — lets a user trace the full chain from CRF item → SDTM variable and understand why a given layout group maps to a given set of SDTM rows. Pitch 2 consumes this key directly in both its CRF and SDTM generation flows.

BcSurrogate handling: where a BC is a BcSurrogate (reference = "None set"), no SDTM Dataset Specialization exists. The view states "No published SDTM Dataset Specialization (BcSurrogate)" rather than returning an empty table. BcSurrogates are not silently omitted — they are the coverage-gap signal this view is meant to surface.

Multiple vlm_group_ids per bc_id: a bc_id can resolve to more than one vlm_group_id — for example a glucose BC appearing in both LB (Laboratory) and FA (Findings About) specializations. The same Activity-context disambiguation logic as in View 3 applies: show all candidates, use Activity context and BC category to filter, require the user to confirm where ambiguity remains. This view and View 3 share the same selection state — a user who has already confirmed a vlm_group_id in the CRF view does not need to re-confirm it here.

This view is read-only browsing only. VLM generation, WhereClause generation, and study-define creation from these rows are covered in Framing Pitch 2.

✍️ Starter Pack of Requirements

  • USDM v4.0 JSON parser — extract studyVersion, epochs, encounters, activities, StudyCells/arms, ScheduleTimeline + ScheduledActivityInstance, biomedicalConceptIds, and bcSurrogateIds into USDM Workbench-native tables.
  • ScheduledActivityInstance (SAI) reference table — kept as its own browsable table, distinct from Encounters; carries SAI.name, timing_day, timing_type, and epoch/encounter linkage, since SAI (not Encounter) is what drives the Schedule of Activities columns.
  • COSMoS BC catalog reference table — bc_id, code, vlm_group_id — loaded once and referenced by both mapping views.
  • COSMoS CRF Specialization reference table (cosmos_crf_item) — imported from the COSMoS GitHub export or the CDISC Library API, keyed on bc_id; includes vlm_group_id as a retained field for the cross-view bridge.
  • COSMoS SDTM Dataset Specialization reference table (cosmos_sdtm_item) — imported from the COSMoS GitHub export, keyed on bc_id and vlm_group_id; includes sdtm_variable, assigned_value, value_list, codelist, mandatory_variable, and dec_id.
  • Study Summary UI — stat tiles with click-to-expand table behaviour.
  • Schedule of Activities renderer — pivot of activity × ScheduledActivityInstance, with epoch/arm/day header rows.
  • BC → CRF Specialization lookup UI — selector, filtered result table, explicit "no match" state, support for more than one matching CRF Specialization per bc_id, and a crf_group_id selection step within the chosen specialization where it resolves to more than one candidate layout group.
  • BC → SDTM Specialization lookup UI — selector (shared with CRF view — the same BC/Activity selection drives both), filtered result table showing sdtm_variable, vlm_group_id, assigned_value, value_list, codelist, mandatory_variable, and dec_id; explicit "No published SDTM Dataset Specialization (BcSurrogate)" state; vlm_group_id visible as the bridge to the CRF side; shared vlm_group_id selection state with the CRF view.
  • vlm_group_id and crf_group_id modelled as stable, joinable fields — no linkage to P21 form or define objects is built in this phase, but both values must be persisted in a form that Framing Pitch 2 can join against without a data model change.
  • Result set display, not single-row display, for a resolved crf_group_id — normalized groups can return many crf_item rows for one group; the UI must show the full set with a visible item count.
  • All four views are read-only in this build — no editing, no save-back.

🐰 Risks & Rabbit Holes

Internal Factors

Sub-timelines are commonly disconnected — intra-day or procedure-level sub-timelines (e.g. a PK sampling schedule) frequently exist in a USDM file as standalone objects with SAI.sub_timeline_id left null, so they will not automatically wire into the Main Timeline SoA. This build renders the Main Timeline only; sub-timeline linkage is a known gap to state clearly, not solve here.

CRF Specialization coverage is genuinely partial — the COSMoS CRF Specialization draft covers 16 domains (2,073 rows), but coverage within domains such as Laboratory is incomplete. The mapping view must surface "no match" honestly rather than imply full coverage exists.

SDTM Specialization coverage varies by domain and surrogate status — BcSurrogates have no published SDTM Dataset Specialization by definition. The SDTM view must state this explicitly and not return an empty table. Even for BiomedicalConcepts, coverage is not complete across all domains, and the 1,475 specializations available as of the research date will grow as COSMoS matures.

A single bc_id can match more than one CRF or SDTM Specialization outright — the same bc_id can appear in genuinely distinct specializations (different domains, different vlm_group_id). Activity context and BC category are the intended disambiguators, but neither is guaranteed to be conclusive or even present. Both mapping views need their own explicit UI treatment (a results list, not a single-row assumption) and must share their selection state via vlm_group_id once a choice is confirmed.

A single bc_id can map to more than one CRF Specialization group — vlm_group_id to crf_group_id is 1:many in some cases. This build resolves any remaining ambiguity through explicit user selection rather than an automatic best-match rule.

BcSurrogate vs BiomedicalConcept must stay visually distinct — collapsing them into a single count in the Study Summary would hide exactly the coverage-gap information this pitch is meant to surface.

Activity category grouping is not a guaranteed USDM feature — category groupings used in exploratory work were authored manually, not read from a defined field. USDM's BcCategory class is optional and sponsors may not populate it consistently. Design and estimation should treat category grouping as a conditional enhancement, with a flat/timeline-ordered activity list as the guaranteed baseline.

External Factors

COSMoS CRF and SDTM Dataset Specializations are still draft standards; domain coverage will change over time, so both "no match" states need to age gracefully rather than requiring UI rework each time CDISC publishes a new domain.

USDM files from different sponsors will vary in completeness and quality — missing sub-timeline links, absent BC references, partial activity metadata. The import step needs to fail gracefully on partial or malformed files rather than blocking the whole import.

❌ No-Gos & Out of Scope

  • CRF form object generation — this build shows what the CRF Specialization says; it does not write a P21 form object. That is Framing Pitch 2, Flow 1.
  • SDTM study define generation — this build shows what the SDTM Dataset Specialization says; it does not write a P21 define object, generate VLM rows, or construct WhereClauseDef / ValueListDef objects. That is Framing Pitch 2, Flow 2.
  • The vlm_group_id → VLM/WhereClause resolution. vlm_group_id is surfaced as a visible bridge key in both mapping views; resolving it into WhereClauseDef and ValueListDef P21 objects is Framing Pitch 2.
  • Value Level Metadata / WhereClause generation (odm_value_list, odm_where_clause).
  • Define-XML or SDTM trial domain generation (TA/TE/TV/TI/TS).
  • Any editing or save-back capability — all four views are read-only.
  • Sub-timeline-aware SoA rendering (PK sampling schedules, insulin clamp sub-schedules, etc.).
  • Automatic CRF form generation or any write/link to a P21 Form Spec library.
